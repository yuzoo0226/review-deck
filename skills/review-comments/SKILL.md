# review-comments: 報告へのレビューに対応する

## 受け取る形式

```
/review-comments <報告ID>

# <報告のタイトル>
台帳: /path/to/reports.json（この id のエントリの file が資料本体）
指摘 N 件です。「@」が指摘箇所の位置（資料のファイル:行／節／同じ文言の何個目か）、「|」で始まる行が報告書からの引用（もともとの本文）、「→」がそこへのレビューコメントです。「→ ✂ 削除提案」は、その引用部分を本文から削除してほしいという指摘です。

[指摘 1/N]
@ 2026-08-13-report.md:1082 ・ 「実験結果」内 ・ 同じ文言の 2/2 個目
| もともとの本文（報告書からの引用。複数行なら各行に | が付く）
→ レビューコメント

[指摘 2/N]
| 別の箇所の引用（位置が取れなかった指摘には @ 行が付かない）
→ そこへのコメント

[指摘 3/N]
@ 2026-08-13-report.md:84 ・ 「仮題」内
| （削除してほしい本文。ユーザが取り消し線を引いた範囲）
→ ✂ 削除提案：この引用部分を削除（理由: 冗長）
```

- **`台帳:` 行** = 報告台帳（reports.json）の絶対パス。報告IDでエントリを引くと `file`（資料の md/html）が分かる。
- **`@` で始まる行** = その指摘が資料のどこかを示す位置。**同じ文言が資料内に何度も出てくる場合、どれを指しているかはこの行でしか分からない**ので、引用文だけで探して最初に見つかった箇所を直さないこと。
  - `ファイル:行` … 報告ディレクトリ内のファイル名と行番号（`1082-1085` のように範囲のこともある）。`Read` の `offset` に使う。
  - `「…」内` … その箇所の直前にある見出し。
  - `同じ文言の n/m 個目` … 資料中に m 箇所ある同じ文言のうち n 番目、という意味。**m ≥ 2 のときは行番号を必ず使って場所を確定する**。
  - `位置は概算` が付いているときは引用が完全一致しなかった（資料が編集された）ということなので、行番号の周辺を読んで自分で位置を判断する。
  - `@` 行が無い指摘は位置を解決できなかったもの。引用文で資料を検索し、複数見つかったら**どれを指しているかユーザに確認する**（勝手に決めない）。
- **`|` で始まる行** = 報告書の中の該当箇所（ユーザが実際に選択した文）。
- **`→` で始まる行** = その箇所へのレビューコメント（＝レビュアーからの指摘）。
- **`→ ✂ 削除提案：…`** = ユーザが本文に取り消し線を引いた指摘。**`|` 行の範囲を資料から削除する**。
  - 文の一部なら、削除したあと前後が自然に繋がるよう句読点・接続を最小限だけ整える。行・段落全体なら行ごと消す。
  - `（理由: …）` が付いていればそれに従う。理由が無くても削除の意図は明確なので、削除する。
  - 削除すると論理が壊れる・必要な情報が消えると判断したときは、勝手に別の文へ書き換えず**「扱わない」＋理由**で返す。
  - 引用は 1000 字で切れることがある。引用の末尾が文の途中で終わっている、または `位置は概算` が付いているときは、削除範囲を確定せずユーザに確認する。
- `| （報告全体について）` は特定箇所ではなく全体への所見。

## やること（この順で）

1. **報告IDから資料を開く**: `台帳:` 行の reports.json で該当エントリを引き、`file` の資料を読む。**指摘箇所は `@` 行の行番号で特定する**（`Read` の `offset` にそのまま渡す）。引用文での検索は `@` 行が無いときの手段であって、`@` 行があるならそちらを優先する。行番号は原則 md（md があれば md）に対するもの。
2. **1件ずつ対応方針を決める**: 各指摘について次のどれかを明示する。
   - **修正する**（何をどう直すか、どのファイルのどこか）
   - **後で扱う**（いつ・どこで扱うか）
   - **扱わない**（理由を必ず書く。「スコープ外」など）
   - 削除提案（`✂`）は「削除した」か「削除せず書き換えた（理由）」かを明示する。
   - 指摘の意味が取れないときは**憶測で埋めずに質問する**。
3. **資料を更新したら台帳を未読に戻す**: reports.json の該当エントリを
   `"status": "unread"` にし、`"reviewResponse"` に対応の要約（1〜3行、日付つき）を書く。
   ユーザが更新版を読み直せるようにするための合図なので、**資料の中身を直したときは必ず行う**
   （「後で扱う」「扱わない」だけで資料を触っていない場合は未読に戻さない）。
   - md とビジュアル版 html の**両方**がある報告は両方を直し、Artifact も同じ URL で republish してから未読に戻す。片方だけ新しい状態にしない。
   - `status` はこの用途以外では触らない（既読にするのはユーザ側の操作）。
4. **返答する**: 指摘ごとに「① 指摘の位置（`ファイル:行`）と要約 → ② 対応（修正/後で/扱わない）→ ③ 反映先のファイル」を1行ずつ並べて報告する。同じ文言が複数ある指摘では、**自分がどの箇所を直したのか行番号で示す**。全部まとめて「対応しました」だけで済ませない。最後に**未読へ戻したかどうか**を1行で書く。
5. **`resolved` は自分で立てない**: コメントの対応済みマークを付けるのはユーザ。こちらは対応内容を返すところまで。

## 注意

- 引用は**ユーザが実際に選択した本文**なので、そこを起点に読む。引用が資料内に見つからない場合は、資料が更新されてズレている可能性があるため、その旨を伝えてから近い箇所で解釈する。
- **同じ文言が複数ある指摘を「全部まとめて」直さない**。`@` 行が指しているのは1箇所だけ。他の箇所も直すべきだと思ったら、その判断を返答に書いてから直す。
- 資料を編集すると以降の行番号がずれる。**指摘は行番号の大きい方から処理する**か、1件直すたびに読み直す。
- 数値・根拠を求める指摘には、**結果ファイル・ログのパスを添えて**答える（記憶や推測で数字を書かない）。
